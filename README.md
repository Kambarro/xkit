## 🎯 Что это

**XKIT** — интерактивный инструмент для развёртывания и обслуживания VPN-сервера на базе **3X-UI + Xray + nginx** под управлением Ubuntu 24.04+.

XKIT автоматизирует установку панели, TLS-сертификатов, маршрутов nginx, подписок и резервного копирования. Панель 3X-UI привязывается к `127.0.0.1`, а снаружи используются только необходимые публичные точки входа.

Дополнительно XKIT умеет:

- создавать профили **VLESS + REALITY + Vision** и **VLESS + XHTTP + REALITY**;
- устанавливать **AmneziaWG** и **Hysteria 2** как инбаунды панели (рекомендуется) **или независимые службы** — обе стороны с AmneziaWG 3.1 (Header Protection);
- подключать зарубежные ноды по SSH и настраивать балансировку Xray;
- показывать состояние сервера в полноэкранном TUI и на веб-дашборде;
- отправлять Telegram-алерты о нодах, сертификатах, аренде и ресурсах сервера;
- выбирать точные версии **3X-UI/Xray** со snapshot, SHA-256, probes и rollback;
- генерировать многостраничный статический сайт-заглушку по сохранённому seed;
- переключать магистральный канал ноды между VLESS TCP/XHTTP REALITY и Hysteria 2 через временный candidate, full-path benchmark и rollback;
- менять IP ноды без переустановки с SSH/API preflight и обновлением certificate pin;
- устанавливать Telegram MTProto только с FakeTLS и pinned Telegram Web Proxy в direct/cascade режиме.

## ⚡ Быстрый старт

### Требования

- Ubuntu **24.04 или новее**;
- доступ `root` или `sudo`;
- архитектура Linux `amd64` или `arm64` для готового TUI;
- домен необязателен: поддерживаются сертификаты для домена, IP и самоподписанный вариант.

### Установка одной командой

```bash
curl -fsSL https://raw.githubusercontent.com/kambarro/xkit/main/install.sh | sudo bash
```

Установщик скачивает ядро, классическое меню, модуль протоколов и TUI нужной архитектуры. Каждый компонент проверяется по SHA-256; при отсутствии или несовпадении суммы установка прекращается.

### Перенос мастера из бэкапа

Положите `xkit-*.tar.gz` в `/root/xkit-restore/` (или используйте существующий `/var/backups/xkit/`) и запустите установку в интерактивной SSH-сессии. Установщик найдёт последний архив и предложит отдельно восстановить сертификаты, пользователей и панель, подписки вместе с панелью, ноды со сроками аренды или весь мастер.

Сертификаты используются только после проверки адреса, срока действия и соответствия ключа. Подписки перегенерируются из восстановленной БД с прежним `XKIT_SUB_TOKEN`; старый nginx-конфиг не переносится. Ноды переподключаются по сохранённым SSH-ключам без переустановки: проверяются SSH/API, новый IP мастера добавляется в активный UFW, затем пересобираются маршруты, балансировка и записи в разделе «Узлы» 3X-UI. Если БД панели не выбрана, сохранённые числовые `panel_node_id` сбрасываются во избежание обновления чужих записей.

Повторное добавление уже записанной ноды предлагает переподключение без нового туннеля. Если реестр потерян, существующий inbound `xkit-tunnel-ИМЯ` используется повторно; полная переустановка ноды остаётся только явным вариантом с бэкапом её БД. В неинтерактивном режиме `-y` автоматический поиск и восстановление не выполняются.

В конце установки можно выбрать:

```text
1) Одиночный сервер — настроить инбаунды и подписки
2) Мастер с нодами — затем подключить зарубежные серверы
3) Ничего — выполнить настройку позже
```

### Запуск после установки

```bash
sudo xkit
```

В интерактивной SSH-сессии откроется полноэкранный TUI. Для классического меню:

```bash
sudo xkit --classic
```

### Обновление

```bash
sudo xkit update
```

Или с явным источником:

```bash
sudo xkit update https://raw.githubusercontent.com/kambarro/xkit/main
```

Обновление сохраняет состояние, конфигурацию, подписки и резервные копии изменённых компонентов. `sudo xkit update --check` только проверяет версию (кэш 6 часов; `--force` — свежий запрос). TUI делает это в фоне и показывает плашку с новой версией; сетевой сбой не мешает работе.

### Неинтерактивный режим

```bash
curl -fsSL https://raw.githubusercontent.com/kambarro/xkit/main/install.sh | sudo bash -s -- -y
```

- `-y` / `--yes` — автоматическое согласие на вопросы;
- `--force` — установка поверх существующей без предварительного меню.

> При использовании `curl | bash` флаги передаются после `-s --`.

### Полное удаление

Три ступени — от аккуратной зачистки до полного вычищения сервера от всех следов:

```bash
sudo xkit uninstall          # xkit + nginx-сайт + cron; бэкап создаётся ОБЯЗАТЕЛЬНО
sudo xkit uninstall --full   # + панель 3X-UI и /etc/nginx/ssl; бэкап обязателен
sudo xkit uninstall --purge  # ВСЁ без сохранений: сервер полностью вычищен
```

Что удаляет каждая ступень:

| | `uninstall` | `--full` | `--purge` |
|---|---|---|---|
| cron xkit, nginx-сайт xkit.conf, `/etc/xkit`, `/var/lib/xkit`, команда `xkit` | ✅ | ✅ | ✅ |
| 3X-UI (сервис, `/etc/x-ui`, `/usr/local/x-ui`) и `/etc/nginx/ssl` | — | ✅ | ✅ |
| бэкапы `/var/backups/xkit` | ✅ сохраняются | ✅ сохраняются | ❌ сносятся |
| `/etc/letsencrypt` (ВСЕ сертификаты, включая не-xkit) | ✅ сохраняется | ✅ сохраняется | ❌ сносится |
| venv certbot (`/opt/certbot-venv`), его units и drop-in, симлинк certbot | ✅ сохраняются | ✅ сохраняются | ❌ сносятся |
| логи `/var/log/xkit-*.log` | ✅ сохраняются | ✅ сохраняются | ❌ сносятся |
| пакеты nginx и certbot | ✅ остаются | ✅ остаются | ❌ сносятся — только если на nginx нет других сайтов |
| UFW-правила SSH/80/443 | ✅ остаются | ✅ остаются | ✅ остаются |

Пояснения:

- `uninstall` и `--full` перед удалением делают обязательный бэкап (провал бэкапа = отмена) и требуют ввести `YES`. Ноды продолжают работать автономно — xray на них не трогается.
- `--purge` — намеренное «без сохранений»: бэкап НЕ создаётся, восстановить ничего нельзя. Подтверждение — ввести `PURGE`. Пакеты nginx/certbot сносятся только если в `sites-enabled`/`conf.d` не осталось чужих сайтов; если остались — xkit сообщит и оставит пакеты.
- Если нужно снести пакеты в обход проверки (осознанно, на пустом сервере): `sudo apt purge 'nginx*' certbot && sudo apt autoremove`.

## 🖥️ TUI и классическое меню

TUI написан на Go с Bubble Tea/Lipgloss и не дублирует логику Bash-ядра: операции выполняются через существующие команды XKIT.

### Навигация

| Клавиша | Действие |
|---|---|
| `↑` / `↓`, `j` / `k` | Перемещение по элементам |
| `Enter` | Открыть раздел или запустить действие |
| `Esc` / `q` | Назад; на главном экране — выход |
| `/` | Поиск пользователей |
| `r` | Обновить состояние |
| `?` | Справка |

На главном экране доступны состояние nginx, 3X-UI и Xray, количество клиентов и нод, срок сертификата и возраст последнего бэкапа. Состояние периодически обновляется через санитизированный snapshot без ключей, UUID, паролей и токенов.

После любой внешней команды — health-check, создания профиля, обслуживания нод, бэкапа и других действий — вывод остаётся на экране до нажатия `Enter`. Код завершения исходной команды сохраняется.

### Когда открывается классическое меню

- после `xkit --classic`;
- при `XKIT_TUI=0 xkit`;
- в pipe, cron и других non-TTY сценариях;
- если TUI для архитектуры недоступен или не прошёл проверку доверия.

## 🛡️ Протоколы и профили

Раздел доступен через TUI, классическое меню и команду `xkit protocols`.

| Профиль | Реализация | Назначение |
|---|---|---|
| **VLESS + RAW/TCP + REALITY + Vision** | Inbound 3X-UI | Основной TCP-профиль |
| **VLESS + XHTTP + REALITY** | Inbound 3X-UI | Альтернативный транспорт без Vision |
| **AmneziaWG** | `awg-quick@awg0` **или инбаунд панели** | Панельный режим (рекомендуется) или отдельная служба; AWG 3.1 (Header Protection) или классический профиль |
| **Hysteria 2** | `xkit-hysteria2` **или инбаунд панели** | Отдельный UDP/QUIC-сервис с Salamander либо панельный режим |

REALITY-сканер показывает только подходящих кандидатов и нумерует их для выбора. Полный технический TSV, включая отклонённые адреса, сохраняется отдельно для диагностики. Тот же порядок выбора используется при сканировании с мастера и с ноды.

```bash
sudo xkit protocols                 # меню профилей
xkit protocols list                 # таблица без секретов
xkit protocols list --json          # машиночитаемая сводка
sudo xkit protocols xhttp           # мастер XHTTP + REALITY
sudo xkit protocols awg             # AmneziaWG: панель (рекомендуется) или служба, клиенты
sudo xkit protocols awg upgrade31   # перевести существующую службу на AWG 3.1
sudo xkit protocols panel install awg  # только панельный инбаунд AmneziaWG
sudo xkit protocols hysteria2       # Hysteria 2: установка и ссылка
sudo xkit protocols panel install   # панельный режим: AWG+Hy2 как инбаунды панели (v6)
```

<details>
<summary><b>Панельный режим (v6.0.0): стабильность прежде всего</b></summary>

- перед включением xkit **эмпирически проверяет ядро панели**: создаёт через API пробный
  инбаунд (`hysteria` / `amneziawg`) на `127.0.0.1`, ждёт слушателя на UDP-порту и удаляет
  пробу. Ядро не умеет протокол — панельный режим для него недоступен, standalone-службы
  продолжают работать как работали;
- один пользователь = записи во всех протоколах сразу (`xkit client all`), одна подписка
  на всё, общий лимит и срок;
- masquerade Hysteria2 отвечает чужим HTTP/3-запросам той же страницей-прикрытием, что и
  nginx (байт-в-байт);
- закрепление ядра: `xkit core-pin 26.6.27` — проверка SHA2-256 по официальному `.dgst`
  релиза XTLS, бэкап и автоперенастройка с откатом, если панель не поднялась.

</details>

<details>
<summary><b>Особенности AmneziaWG и Hysteria 2</b></summary>

- **AmneziaWG 3.1** (v7.2.7): PPA amnezia раздаёт AWG 3.1 с 12.08.2026 — кит определяет реальную версию по `awg --version` и генерирует **полный профиль 3.1**: `HeaderProtectionKey` (шифрование заголовков ChaCha20), паддинги `S1–S4` (все ≥ 12), `H1–H4 = 1/2/3/4` (документированный режим совместимости с Header Protection), `ContentPaddingAddition`, тайминг-диапазоны (rekey/reject/keepalive), `MTU 1280`, `I1`. `RandomTrailers`/`DisableCookies` по умолчанию выключены (до фикса бага классификатора в апстриме). Классический профиль остаётся для старых клиентов/роутеров; перевод живой установки — `xkit protocols awg upgrade31` (перезапишет серверный и все клиентские конфиги, с бэкапом и откатом). Клиентские конфиги хранятся в `/root/xkit-awg/` (права 700/600) и наследуют весь блок обфускации сервера автоматически. Чужая установка AWG без метки XKIT не удаляется. При активном UFW добавляются входящее UDP-правило и два route-правила forwarding с меткой XKIT; при удалении очищаются только они. Клиенты для 3.1: AmneziaVPN ≥ 5.0.1.5, AmneziaWG ≥ 3.1, WG Tunnel ≥ 5.6, свежий Mihomo.
- **Hysteria 2** загружается из официального релиза вместе с `hashes.txt`; совпадение SHA-256 обязательно. Используется Salamander, создаются systemd-служба, UDP-правило UFW с меткой XKIT и клиентская `hy2://` ссылка. Standalone отдаёт локальный file-camo из `/var/www/camo`; панельный режим эмпирически проверяет file-masquerade и при необходимости использует самодостаточный HTML со встроенными CSS/SVG. Активная проверка: `xkit protocols hy2 camo-check` (для панельного режима — `xkit protocols panel camo-check`).
- **Портовые профили:** balanced — AmneziaWG `UDP 443` + Hysteria 2 `UDP 8443`; hy2-first — Hysteria 2 `UDP 443` + AmneziaWG `UDP 51820`. TCP и UDP независимы, поэтому эти UDP-порты совместимы с REALITY/nginx на `TCP 443`. Два TCP-сервиса на одном `IP:443` по-прежнему несовместимы. Список: `xkit protocols ports`.
- XKIT не включает неактивный UFW автоматически и не удаляет чужие правила. Существующий общий `allow` учитывается без создания дубля; ошибки настройки firewall или сохранения состояния откатывают установку нового профиля.

</details>

> **Важно:** локальный статус службы не гарантирует прохождение DPI у конкретного клиентского провайдера. Результат зависит от сети, UDP, репутации IP и выбранных параметров.

## 🧭 Меню

Классическое главное меню разделено на шесть групп:

| Группа | Что внутри |
|---|---|
| **1. Установка и настройка** | Установка, автопроброс, скрытие панели, relay и externalProxy |
| **2. Пользователи** | Создание, удаление, список, сброс трафика и подписки |
| **3. Протоколы** | REALITY, XHTTP, AmneziaWG, Hysteria 2, ключи и сводка |
| **4. Ноды** | Добавление (с авто-API-токеном панели), состояние, стратегии, repair, repin, relogin и удаление |
| **5. Обслуживание** | Сертификат, health-check, статус, бэкап, restore и update |
| **6. Мониторинг** | Дашборд, Telegram, сроки аренды, SSH-автоменю и реквизиты |

## 🧩 Возможности

### Установка и панель

<details>
<summary><b>3X-UI, nginx, TLS и предварительные проверки</b></summary>

- установка официального 3X-UI и необходимых системных пакетов;
- при новой установке пароль мастера заменяется на 32 случайных символа; пароли панелей новых нод также имеют длину 32 символа, а `install-result.env` обновляется атомарно;
- привязка панели к `127.0.0.1` и обратный прокси через nginx;
- Let's Encrypt для домена или IP, собственные файлы либо самоподписанный сертификат;

### Магистральные профили и смена IP (7.1)

```bash
xkit nodes profile list
xkit nodes profile switch node-1 vless-xhttp-reality
xkit nodes profile switch node-1 hysteria2
xkit nodes profile benchmark node-1
xkit nodes readdress node-1 203.0.113.20 --dry-run
xkit nodes readdress node-1 203.0.113.20
xkit nodes tune node-1 balanced
```

Переключение создаёт один временный candidate на свободном порту, меняет master outbound и скачивает 8 MiB через весь активный каскад. После успеха старый inbound удаляется; при ошибке восстанавливаются registry, master template и owned firewall-правила. RTT/throughput не являются client/DPI test. Клиентские подписки мастера не меняются. AWG 3.1 остаётся external/host-level вариантом: автоматический switch отклоняется, поскольку Xray не имеет AWG outbound.

Смена IP требует тот же SSH host key, успешные SSH/API preflight и новый pin панельного TLS. Переустановка 3X-UI/Xray и автоматический перевыпуск REALITY не выполняются. Сертификат Hysteria/TLS меняется только при необходимости SAN.

### Telegram Proxy (7.1)

Доступны только **MTProto FakeTLS** (`ee…`) и официальный **Telegram Web Proxy** `tproxy-server`, в direct/cascade режиме. SOCKS5 отсутствует. Для Web Proxy обязательны pinned commit и SHA-256 архива; `latest` запрещён. Direct требует выделенную x86_64 ноду со свободными 80/443 и без существующего Caddy. Cascade использует loopback relay/backend/admin, nginx base path и не логирует URI. `/readyz` не заменяет реальный Telegram WEB client test; upstream Web Proxy остаётся proof-of-concept.

## 🛠️ Эксплуатация XKIT 7

### TCP Fast Open и TCP_NODELAY (7.4.3)

`xkit sockopt on` включает серверный бит `net.ipv4.tcp_fastopen=3` и добавляет `tcpFastOpen` + `tcpNoDelay` TCP-инбаундам VLESS/VMess/Trojan. `off` снимает только sockopt, установленный xkit; чужие настройки не изменяются. `status` показывает состояние sysctl и инбаундов. Для отключения sockopt при создании REALITY/XHTTP задайте `XKIT_SOCKOPT=0`.

### Ноды: plan → canary → остальные

```bash
xkit nodes plan --json
xkit nodes apply --canary node-1
xkit nodes apply --remaining
```

`plan` ничего не меняет. Apply привязан к SHA-256 исходного реестра: после изменения нод план нужно пересоздать. Canary проверяет только TCP, SSH и API выбранной ноды; это не внешняя client/DPI-проверка. `--remaining` отклоняется до успешного canary.

Scoped API token сохраняется в root-only node record и передаётся curl через защищённый header-файл, а не argv. Поддержка Bearer-токенов зависит от версии 3X-UI; старый password login остаётся fallback. `nodes token remove` удаляет только локальную копию и не отзывает токен в самой панели.

### Проверка нод и заморозка ТСПУ (7.3)

```bash
xkit nodes check node-1 --deep     # одна нода, детально (CPU/RAM/диск/версии/серт)
xkit nodes check all --json        # все ноды, JSON (включая freeze-вердикты)
xkit nodes freeze node-1           # замер «заморозки» ТСПУ на леге мастер→node-1
xkit nodes freeze                  # таблица сохранённых вердиктов
```

`nodes check` проверяет одну ноду или все сразу: TCP туннеля (с RTT), SSH, панель (API) и службу x-ui; `--deep` добавляет CPU/RAM/диск, версии 3X-UI/Xray и срок серта панели. Коды выхода: 0 — все в норме, 2 — есть проблемы, 1 — нода не найдена.

`nodes freeze` измеряет «заморозку» ТСПУ на леге мастер→нода. Идея и логика замера заимствованы из **freeze-check** (https://github.com/MarkSinD/freeze-check, MIT License): на ноде на 2–3 минуты поднимается временный HTTP-сервер — случайный порт, 2 МБ файл по случайному токен-пути, systemd-run с RuntimeMaxSec, ufw-дыра закрывается автоматически (при обрыве сессии всё убирает trap, а страховочный systemd-таймер на самой ноде чистит её даже при гибели мастера). Мастер скачивает 256 КБ три раза и агрегирует вердикт: `ok` / `unstable` (повторите) / `frozen` — обрыв после первых килобайт, фирменная заморозка ТСПУ без RST / `nothing` — не пришло ничего (частый вид той же заморозки на мобильных, либо порт закрыт security-group провайдера). Вердикты хранятся в `/etc/xkit/nodes-freeze.json` (0600) и видны в `nodes check --json` и в freeze-таблице.

Валидность: замер ведётся **с мастера**, поэтому вердикт применим к провайдеру и региону мастера — для каскада «мастер в РФ» это и есть измеряемый RF→foreign участок. Если мастер выходит в мир не через RU, xkit предупредит и спросит подтверждение. Это не client/DPI-тест: проверяется живость TCP-канала под объёмной передачей, а не имитация клиентского трафика. `frozen`/`nothing` — варианты лечения: `xkit protocols` (AmneziaWG/Hysteria 2 — UDP не страдает от TCP-заморозки) или `xkit nodes readdress` (сеть кандидата проверьте заранее freeze-check'ом вручную).

### Учёт трафика

```bash
xkit ledger collect
xkit ledger show
xkit ledger quota-check 107374182400
```

Ledger использует read-only `clientStats` без `statsquery -reset`. Первый сбор задаёт baseline; далее учитываются только положительные дельты. Повторный сбор не удваивает трафик. После reset/restart счётчика XKIT не вычитает трафик и не пытается угадать расход за пропущенный интервал. `quota-check` — только диагностика: автоматического отключения пользователей нет.

### Обслуживание и обновления

- `maintenance install` создаёт logrotate и ежедневный systemd timer; `restart apply` выполняет только разрешённые службы XKIT и проверяет nginx перед перезапуском;
- `geodata update` принимает только точный tag и обе SHA-256 суммы; `latest` запрещён. Перед заменой выполняются резервная копия и config test, при ошибке старые файлы возвращаются;
- `doctor export` удаляет UUID, пароли, токены, приватные ключи, cookie, subscription URL и IP из support bundle. Перед отправкой bundle третьим лицам всё равно следует просмотреть его вручную;
- `backup verify` и `restore --dry-run` не меняют систему. `backup export` требует локально установленный `age` и не отправляет архив в Telegram;
- Telegram bot обслуживает только `/status`, `/report`, `/start`, `/help`, numeric allowlist и rate limit. Shell, управление клиентами, произвольные запросы и передача бэкапов отсутствуют.

REALITY scanner предназначен только для разрешённых целей. Массовое сканирование может нарушить правила VPS-провайдера; CSV с issuer/TLS/cipher/ALPN помогает диагностике, но не доказывает устойчивость к DPI.

## 🔒 Безопасность

| Механизм | Назначение |
|---|---|
| SHA-256 manifest и pin-хэши | Не устанавливать компоненты без проверенной суммы |
| Fail-closed установка и обновление | Ошибка проверки останавливает операцию |
| Проверка доверенных каталогов | Запрет небезопасных прав и загрузки root-кода из `/tmp` |
| Панель на `127.0.0.1` | Панель не публикуется напрямую |
| `nginx -t` и резервная копия | Откат при ошибке конфигурации |
| SSH host key и certificate pinning | Защита подключений к нодам |
| Секреты через stdin | Пароли и токены не передаются в аргументах команд |
| Санитизированные snapshot и dashboard | Не раскрывать UUID, ключи, пароли и токены |
| Права `700` / `600` | Ограничение доступа к состоянию и клиентским конфигам |
| Проверка архивов | Безопасное восстановление без опасных путей и symlink |
| Подтверждение установщика 3X-UI | Официальный инсталлятор (мастер и ноды) запускается от root только после явного ответа; `XKIT_YES=1` — для автоматизации |
| Подпись релизов Ed25519/SSHSIG (v6.0.0) | `SHA256SUMS` + отсоединённая подпись; install.sh проверяет `ssh-keygen -Y verify` (namespace `xkit-release`) и содержимое манифеста; битая подпись = отказ, отсутствие — фолбэк на pin-книгу |
| Пин апстрима (v6.0.0) | `XKIT_XUI_SHA256` — сверка установщика 3X-UI (расхождение = подтверждение); `xkit core-pin` — ядро Xray с проверкой официального `.dgst` |
| Порт/путь существующей панели (v7.2.3) | `XKIT_PANEL_PORT` и `XKIT_WEB_BASE_PATH` — явный override, если панель уже стояла до xkit и её настройки не определились автоматически (install-result.env, `x-ui setting -show true`, БД) |
| Certbot сразу актуальный (v7.2.4) | certbot ставится одним шагом в venv (без промежуточного пакетного 2.9); `XKIT_CERTBOT_VERSION` — опциональный пин версии по образцу `XKIT_3XUI_TAG`; PyPI недоступен — фолбэк на пакетный certbot (доменные серты работают, IP-нет). Автопродление — ровно один путь: drop-in к `certbot.service` или свой `xkit-certbot.timer` (дважды в сутки) |
| Security-обновления (v7.2.4) | xkit не делает `apt upgrade` сам (ребут ядра и перезапуск сервисов — решение администратора), но перед установкой показывает, сколько security-обновлений в очереди и запрошен ли ребут |
| API-токен панели (v7.2.5) | 3X-UI v3.11+ выдаёт при установке `XUI_API_TOKEN` (install-result.env) — xkit сохраняет его в `xkit.env` и ходит в `/panel/api/*` с `Authorization: Bearer` (CSRF панели bearer-запросы пропускает); логин/пароль остаётся фолбэком для старых панелей |
| Усиление пароля с проверкой (v7.2.5) | Пароль панели меняется реальным бинарником `/usr/local/x-ui/x-ui` (обёртка `/usr/bin/x-ui` подкоманду `setting` не форвардит и молча выходит с 0) и проверяется логином в API; не применился — честный откат, а не ложное «усилен» |
| Полный лог установки (v7.2.5) | В `/var/log/xkit-install-*.log` пишется весь вывод установки, а не только шаги со спиннером; анимация спиннера в лог не попадает |

xkit-tui-linux-arm64          # TUI для ARM64

```text
README.md                     # документация проекта
build.sh                      # сборка ядра из src/, TUI и обновление контрольных сумм
src/                          # ИСХОДНИКИ ядра: 25 модулей, из которых собирается xkit.sh

tests/                        # регрессионные и интеграционные тесты
nginx-xray-manager-v3.sh      # предыдущая версия для совместимости
```

Начиная с v5.3.1 ядро `xkit.sh` — СОБИРАЕМЫЙ файл: правки вносятся в модули
`src/[0-9][0-9]_*.sh` (порядок модулей задаётся номером в имени), затем
`build.sh` склеивает их в `xkit.sh`, пересобирает TUI и обновляет контрольные
суммы и пин-книгу. Править сам `xkit.sh` напрямую нельзя — правка будет
затёрта при следующей сборке.
```

После изменения поставляемых компонентов выполните:

```bash
bash build.sh
sha256sum -c xkit.sh.sha256
```

## ❓ FAQ

<details>
<summary><b>Команда xkit сразу открывает TUI?</b></summary>

Да, после установки в интерактивном терминале. Используйте `xkit --classic`, если нужно прежнее Bash-меню.

</details>

<details>
<summary><b>Нужен ли домен?</b></summary>

Нет. Можно использовать IP и поддерживаемый вариант сертификата. Для некоторых сценариев маскировки REALITY собственный домен и сайт могут быть предпочтительнее.

</details>

<details>
<summary><b>Можно ли установить поверх существующего 3X-UI?</b></summary>

Да. XKIT может подхватить существующую установку и скрыть панель за nginx. Перед чистой переустановкой создаётся бэкап, но клиенты и инбаунды панели затем пересоздаются.

</details>

<details>
<summary><b>Чем update отличается от reinstall?</b></summary>

`xkit update` обновляет компоненты и сохраняет текущее состояние. `xkit reinstall` выполняет бэкап, полное удаление и установку с нуля.

</details>

<details>
<summary><b>Показывает ли health-check гарантированный обход DPI?</b></summary>

Нет. Он показывает локальное состояние служб и маршрутов. Доступность для клиентов необходимо проверять отдельно у реальных провайдеров.

</details>

<details>
<summary><b>Можно ли использовать XKIT без TUI?</b></summary>

Да. Доступны классическое меню и CLI-команды для cron, CI и автоматизации.

</details>

## 🛠️ Устранение проблем

<details>
<summary><b>Установщик сообщает о несовпадении SHA-256</b></summary>

Не обходите проверку. Убедитесь, что `install.sh`, компоненты и `xkit.sh.sha256` относятся к одному коммиту. После редактирования выполните `bash build.sh` и опубликуйте обновлённые pin-хэши и manifest вместе.

</details>

<details>
<summary><b>Панель не открывается через nginx</b></summary>

```bash
sudo xkit health
sudo systemctl status nginx x-ui
sudo nginx -t
```

Также проверьте DNS, сертификат и `/var/log/nginx/error.log`.

</details>

<details>
<summary><b>Не приходят Telegram-алерты</b></summary>

```bash
sudo xkit telegram check
sudo xkit telegram test
```

Если прямой доступ к Telegram API недоступен, для доставки через ноды нужна хотя бы одна работающая нода.

</details>

<details>
<summary><b>Нужно найти журнал установки</b></summary>

```bash
sudo ls -lt /var/log/xkit-*.log
```

</details>

## 🧩 Версии компонентов и сайт-заглушка

```bash
xkit versions list
xkit versions status
sudo xkit versions install 3.11.0 26.10.31
sudo xkit versions rollback
xkit camo status
xkit camo files
sudo xkit camo regenerate
```

Менеджер версий скачивает только точные теги официальных релизов и **отказывается работать без совпавшей SHA-256**. Перед сменой сохраняются `/usr/local/x-ui`, БД и настройки; после неё проверяются версии, `xray run -test`, systemd и локальный ответ панели. При ошибке прежняя связка восстанавливается автоматически. Записи `candidate` в манифесте — лишь допуск к этим проверкам, не гарантия совместимости. Downgrade 3X-UI по умолчанию запрещён из-за схемы БД.

При первичной установке можно нажать `v` на шаге 3X-UI либо заранее задать `XKIT_3XUI_TAG`, `XKIT_XRAY_VERSION` и обязательный `XKIT_XUI_SHA256` для установщика панели. Автоматических обновлений нет.

Если 3X-UI уже стоял на сервере до xkit, а порт и webBasePath не определились автоматически, установщик спросит их интерактивно; в сценариях (CI, curl-пайп без TTY) задайте их заранее: `XKIT_PANEL_PORT=2053 XKIT_WEB_BASE_PATH=/ bash xkit.sh install`.

Camo смешивает тему, раскладку, палитру, шрифт, контент и локальную SVG-графику. Seed хранится в `/etc/xkit/camo.env`; перезапуск и починка поверх сайт не меняют. Команда `regenerate` без аргумента создаёт новый случайный seed; `regenerate <64-hex-seed>` воспроизводит заданный вариант. Внешние CDN, реальные бренды и формы сбора данных не используются.

**Ручная замена сайта.** Команда `xkit camo files` выводит актуальные пути. Заменить можно `index.html`, `about.html`, `contact.html`, `privacy.html`, `404.html`, `assets/style.css` и `assets/mark.svg` в `/var/www/camo/`. Ссылки на CSS/SVG должны оставаться локальными. Перед правкой сделайте копию: `sudo cp -a /var/www/camo /var/www/camo.manual-backup`. Перезапуск nginx после замены статических файлов не нужен. Следующая `camo regenerate` полностью перезапишет ручные правки; чтобы их сохранить, не запускайте регенерацию либо держите отдельную копию. Это убирает единый шаблонный HTML-фингерпринт, но **не меняет TLS/nginx/REALITY и сетевое поведение и не гарантирует обход DPI**.
